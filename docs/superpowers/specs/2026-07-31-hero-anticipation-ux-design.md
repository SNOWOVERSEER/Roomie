# Hero 首屏可预测性 UX 设计

日期：2026-07-31
状态：已批准，待实施

## 问题

桌面端进入首屏后，用户看到的是一张静止的 poster，右侧一片空白。视频起播、标题浮现都要等一会；等到画芯换画这个 feature 露面，已经是第 11.5 秒。用户没有任何理由相信"再等等会有东西"，很可能直接下滑走掉。

量化下来是三件独立的事：

**1. 首屏关键路径 ~14MB，其中一半在跟自己抢带宽。**
`ArtworkSwitcher` 的画框图层为"杜绝闪白"把 6 张 `art-0X.png`（合计 7.1MB）全部立即挂载，而 `rect` 在挂载首帧就有值。于是 7.1MB 的 PNG 和 6.7MB 的视频同时开下。这些画在第 11.5 秒之前根本用不上。

**2. 标题的出现绑在视频时间上，不是页面时间。**
`onTime` 里判断 `v.currentTime >= HERO_TIMINGS.title`。视频不起播 → `currentTime` 恒为 0 → 标题、副标题、CTA 全部不存在。加载期间首屏是真的没有内容，不是"晚一点浮现"。

**3. 完整剧场 12.3 秒，中途零信号。**
视频 10.0s → 定格 → +0.68s CTA → +1.5s 画芯架 → +2.3s 滚动提示。从起播到画芯架露面 11.5 秒，期间没有任何东西告诉用户还有内容在后面。

## 方案总览

先把自伤的等待砍掉（第 2 节），再用叙事让剩下的等待值得等（第 1 节）。加载指示器是对"必须等"的妥协，而这里的等待有一半是自己造成的。

核心叙事决定：**画芯不"淡入"，它被推进来。** 复用 CTA 里已有的 `roomie-pushing-cat.png`——"猫推画 = 换画"这个视觉语汇全站已经建立。正在被推进来的东西天然就是不能碰的，不需要任何 disabled 态的说明；推到位那一刻就是"现在轮到你了"。

拆成两段以避开双猫同框：视频里的猫全程在动（走进 → 抓画 → 坐下），若插画猫同时出现，画面里会有两只黑白猫。因此**货先行、猫后到**——画芯先自己滑进来（推手在画面外，悬念更足），猫留到定格后登场，成为 payoff 而非铺垫。

### 素材事实（已验证）

- 视频固定机位：0s / 6s / 8s / 9.9s 四帧中家具、地毯、画框、边几位置完全一致
- 画框左侧 6%–23% 区间（rack 定位在 12.9%）全程是空的踢脚线 + 木地板，叠加图层不会穿帮
- 画面左缘的木柜可作猫的入场遮挡，动线在这个房间里说得通
- 桌面端各视口下 `object-fit: cover` 均为上下裁切、左右不裁，故"从画面左缘进来"在 PC 上始终成立
- `roomie-pushing-cat.png` 是朝右推的姿势，与从左往右的动线一致；花色与视频中的猫一致

## 第一节：时间轴与叙事

### 加载期（页面时间，不依赖视频）

| 时间 | 事件 |
|---|---|
| `t=0` | poster 显示；右下角爪印环出现，走**不定长慢弧**（此时确实不知道要多久，诚实的 indeterminate） |
| `t=400ms` | 视频若仍未起播 → **标题按页面时间淡入**，不再等视频 |
| `t=2.0s` | 副标题兜底同理 |

性能修复后加载期通常只有几百毫秒，indeterminate 段几乎不可见。

### 演出期（视频时间）

| 时间 | 事件 |
|---|---|
| 起播 | 爪印环切成**确定进度**，走完 = 可交互 |
| 0.6s | 标题（若尚未因兜底出现） |
| 2.6s | 副标题 |
| **7.0s** | **前 5 张画芯从舞台左缘依次滑入，去饱和态；推手在画面外** |
| 10.0s (`onEnded`) | 视频定格；文字上移收拢（`settled`） |
| +0ms | **猫从左缘柜子后探出，推第 6 张（最后一张）到位** |
| +550ms | CTA 浮现（与猫的动作并行，不排队） |
| +900ms | 猫推到位、退场 |
| +1000ms | **画芯落定：上色、投影、吊牌浮现 → 可交互**（`plaque`） |
| +1500ms | 滚动提示（`cue`） |

演出总长 12.3s → 11.5s。**可交互时刻**（用户真正能动手的那一刻）是起播后 **11.0s**——这是 SkipDial 进度环的终点，`cue` 在其后 500ms，不计入环的长度。

真正的收益在感知：画芯露面从第 11.5 秒提前到第 7 秒，用户提前 4.5 秒知道有东西在来。

滑入分 5 + 1 而非 6 + 0，是为了让猫推的那一下有实际内容可推——猫空手进来摆姿势会露馅。第 6 张的空位在前 5 张滑入后就留在那里，本身也是一个"还没完"的提示。

### SkipDial（爪印进度环 + 跳过）

右下角一个控件，同时承担两件事：

- **进度环本身 = 可预测性。** 必须是有终点的确定进度，不能是无限转圈。无限转圈表达的是"我不知道还要多久"，恰恰是反可预测性的、促使人划走的东西。一个走到 70% 的环说的是"再 3 秒就好"。环的长度 = 起播到可交互 = **11.0s**。
- **hover = 控制权。** 中心的爪印换成 "Skip"，不想等的人不用等。

加载期点它 = 直接进静态定格态，给弱网用户一个逃生舱。

移动端不出现（走 staticMode，本来就只有 350ms 错峰，没有可跳过的等待；hover 在触屏上也不存在）。

## 第二节：性能

| 项 | 现状 | 改成 |
|---|---|---|
| 6 张 art PNG | 挂载即全下，7.1MB，与视频抢带宽 | 推迟到视频起播后才设 `src`；art-01 优先。另转 WebP，7.1MB → ~1.5MB |
| 视频 | 1664×1248 / 5.4 Mbps / 6.7MB | 降到 1280×960、CRF 26–28，目标 ~1.8MB；加 WebM 作首选 `<source>`，H.264 兜底 |
| 标题时机 | 绑 `video.currentTime`，视频不播就永不出现 | 页面时钟兜底（见第一节） |

首屏关键路径从 ~14MB 降到 ~2MB 量级。

视频重压需在实施时用 ffmpeg 试几档并肉眼比对画质后定档，不预设参数。WebP 转换涉及既有管线 `tools/make_artworks.py`，改动需保持 `frame-rect.json` 的自动测量输出不变。

## 第三节：组件结构

`Hero.tsx` 现为 216 行，同时管状态机、布局和四个装饰层。新增猫送货 + 进度环 + 延迟加载会使其失控，因此本次一并理清边界。

### 抽出 `useHeroSequence()`

把时间轴状态机（`staticMode` / `beats` / `steps` / 定时器清理）从 `Hero.tsx` 搬进 hook，`Hero.tsx` 只剩渲染。新增的兜底时钟和 skip 重入防护都长在状态机上，这是本次改动最大的受益者。

### 状态模型

不推翻现有结构。`beats` / `steps` 错峰布尔工作良好，只加一个：

- `beats.delivery` — 视频 7.0s 触发，画芯开始滑入

rack 的视觉态由两个已有布尔决定，无需引入 phase 枚举：

| `delivery` | `revealed` | rack 表现 |
|---|---|---|
| false | false | 不在场 |
| **true** | false | 滑入中 · 去饱和 · `pointer-events: none` |
| true | **true** | 落定 · 上色 · 投影 · 可交互 |

去饱和的判据不是某个具体数值，而是：**截图给没看过这个页面的人，他应当读得出"这堆东西还没准备好"，而不是"这堆东西坏了/是灰的"。** 实施时以第五节的 7.0s 截图为准反复调，宁可欠一点也不要看起来像 disabled 的报错态。

`prefers-reduced-motion` 与移动端 staticMode 下 `beats.delivery` 与 `steps.plaque` 同时置 true，rack 直接进入落定态，不经过去饱和阶段。

### 新组件

两个都自包含，各自一件事：

- `components/Hero/CatDelivery.tsx` — 猫推货层。props `{ rect, play }`，`play` 由 false 翻 true 时播一次进场→推到位→退场的完整动作，此后不再响应。定格时触发
- `components/Hero/SkipDial.tsx` — 爪印进度环 + skip。props `{ mode: "buffering" | "running", durationMs, onSkip }`

### art 延迟加载

`ArtworkSwitcher` 新增 `loadArt` prop，由 Hero 在视频起播时（≈0.5s）置 true 后才挂 `<img>`。距离定格还有 10 秒，解码时间绰绰有余，不会闪白。

### 配置

新增时间常量（delivery 时机、猫的动画时长、SkipDial 总时长）统一进 `lib/heroConfig.ts` 的 `HERO_TIMINGS`，保持"调体验不碰组件逻辑"的既有约定。

## 第四节：降级与边界

| 情况 | 行为 |
|---|---|
| `prefers-reduced-motion` | 全量直呈；猫送货不播；SkipDial 不出现 |
| 移动端 `≤760px` | staticMode 快速错峰，维持现状；猫不播（静图上没有铺垫，推货会突兀）；SkipDial 不出现 |
| autoplay 被拒 / 视频 `error` | → staticMode，同上 |
| **视频 8 秒仍未 `canplay`** | **新增**：自动降级 staticMode。现无此兜底，弱网会一直卡在 poster |

### Skip 重入防护

视频播放中执行 skip 需 `currentTime = duration` + `pause()`，这会触发 `ended` 事件 → `runFreezeSequence(false)` 二次执行，与 skip 的 `runFreezeSequence(true)` 打架。需一个 `skipped` ref 让 `onEnded` 提前 return。这是本次最容易漏的坑。

## 第五节：验证

时序 + 视觉功能，单测价值有限。以下用浏览器实跑验证，不依赖人工目测：

1. **网络瀑布** — 确认 art PNG 的请求晚于视频起播。这是整个性能修复成不成立的判据
2. **三个时刻截图** — 7.0s（画芯滑入中、去饱和）/ 10.0s（猫推货）/ 11.5s（落定），确认坐标未错位
3. **慢网** — 模拟弱网确认标题兜底在 400ms 触发，而非干等视频
4. **reduced-motion + 移动视口** — 确认猫不播、SkipDial 不出现
5. **Skip 重入** — 播放中点 skip，确认不因 `ended` 二次触发而闪

## 建议实施顺序

三块改动互相独立，但价值上有先后。按此顺序做，每一步都能单独验证并且随时可停：

1. **性能 + 标题解耦**（第二节）。这是"进去啥也没有"的正解，不修的话后面的叙事就是在装饰一块空屏
2. **`useHeroSequence()` 抽取**（第三节）。纯重构，行为不变，为后面两步腾地方
3. **SkipDial**（第一节）。自包含，装上就有可预测性收益，不依赖猫
4. **画芯滑入 + CatDelivery**（第一节）。视觉分量最重、调参最费时间的一块，放最后

## 明确不做

- 不加无限转圈的 spinner（反可预测性，见第一节）
- 不在画芯架上再叠一个加载指示（"正在被推进来 + 去饱和"已说清楚；转圈控件叠在写实客厅照片上会打碎场景感）
- 不改视频素材本身（固定机位与落幅帧是 `FRAME_RECT` 坐标的基准）
- 不动 `Hero.tsx` 顶部备忘里规划的 HeroCarousel 结构；本次改动应保持该升级路径可行
